01 · Introduction

Why build a tracing bot now

Distributed tracing is the richest signal for diagnosing failures in microservice systems, yet in 2026 it remains the least automated pillar of observability. Research across current tool rankings and practitioner reports shows a consistent split: open-source tracing tools (Jaeger, Zipkin, Grafana Tempo) collect and display traces well but stop there — no alerting, no root-cause analysis, no natural-language access. Commercial platforms (Datadog APM, Dynatrace) automate analysis with AI, but at high and unpredictable cost, behind proprietary lock-in, and with sampling and retention limits that can discard the very traces needed during an incident.

TraceIQ is an AI-native tracing agent that closes this gap. It is an OpenTelemetry-native bot sitting on an open, cost-efficient trace store, doing what engineers currently do manually: watch traces continuously, detect anomalies, run evidence-grounded root-cause investigations, correlate traces with logs and metrics, answer questions in natural language, and propose — with human approval — safe remediations. It brings Dynatrace-class RCA and Datadog-class agentic investigation to the open-source stack, without the bill shock or the lock-in.

  • No natural-language tracing UX on the open-source stack. TraceIQ: chat-first interface over open trace data.
  • Remediation stops at suggestion — AI SRE tools remain copilots with no guardrail standards. TraceIQ: read-only default, scoped action allowlists, human approval gates, per-incident action budgets.
  • AI agents are bounded by telemetry quality — an agent cannot reason over a trace that was sampled away. TraceIQ co-designs the sampler and the agent: the agent tells the sampler what "interesting" looks like.

The anomaly-aware sampler retains all interesting traces and downsamples healthy ones into cheap object storage, while a small ClickHouse hot index carries error signatures, RED metrics, and topology edges. 05 · Detailed low level architecture

Tier-by-tier specification

1 — Ingest & sampling tier

  • Protocols: OTLP gRPC (4317) and HTTP (4318) first-class; Jaeger Thrift/gRPC and Zipkin v2 JSON accepted for migration. Built as an OTel Collector distribution (the Jaeger v2 pattern) to reuse the receiver/processor ecosystem.
  • Anomaly-aware tail sampler (the differentiator): spans buffered per trace-ID in a consistent-hash ring so complete traces assemble on one shard; Kafka/Redpanda as the buffering substrate (the decoupling pattern Tempo 3.0 adopted). Per completed trace: keep 100% if error status, latency above p99 baseline, rare path signature, or match on an active-investigation predicate pushed down by the RCA engine; otherwise downsample to a configurable floor (default 1%), with per-service RED metrics always extracted before discard.
  • Path signatures: hash of ordered (service, operation) edges; a signature unseen for N days is rare and kept.
  • Budget: sampling decision within 30 s of trace completion; zero latency added to the request path.

2 — Storage tier

  • Cold store: Parquet trace blocks on object storage (columnar, zstd). Default retention 30 d anomalous / 7 d healthy-sample, per-tenant configurable. Open format — exportable, DuckDB/Athena-queryable.
  • Hot index (ClickHouse): span rollups, error signatures (exception type + stack fingerprint), topology edge table at 10 s resolution, exemplar trace-IDs per histogram bucket. Sized at 2–5% of raw span volume (Jaeger v2.18's ClickHouse move showed 8.6× compression on 10 M spans).
  • Correlation contract: trace_id injected into logs, exemplars attached to metrics, W3C traceparent canonical with B3 accepted.

3 — Anomaly detection tier

  • Streaming baselines per (service, operation): latency quantiles (t-digest), error rate (EWMA), throughput — seasonally adjusted.
  • Detectors: latency shift, error burst, new error signature, topology change, and deploy-marker correlation (ArgoCD/Flux/GitHub webhooks tag spans with version).
  • Output is an anomaly event, not an alert: events are deduplicated by topology proximity into incident candidates — the anti-alert-fatigue layer.

4 — Agentic RCA engine (the core)

  1. Contextualize: pull topology neighborhood, recent deploys, active anomalies, and similar past investigations from memory.
  2. Hypothesize: the LLM generates ranked hypotheses ("v2 deploy of payment-svc introduced N+1 DB calls").
  3. Test: each hypothesis compiles to concrete queries — structural trace queries, index queries, log searches, PromQL — executed as tool calls against real data. No hypothesis survives without evidence.
  4. Validate / iterate: confirming evidence promotes; contradicting evidence discards; loop until confidence threshold or budget exhaustion.
  5. Report: root-cause narrative, cited evidence (trace-IDs, log lines, metric charts), blast radius from topology, suggested remediation.

Transparency contract: every step is persisted as a replayable investigation log. An engineer can mark any step wrong; the correction becomes retrieval-weighted memory. Budgets: per-investigation token, time, and query caps (default 5 min). Models: pluggable LLM backend (Claude API default; local model for air-gapped) using structured tool-calling only — the model never sees raw span dumps. Evals: ships with an SREBench-style fault-injection suite; accuracy numbers are published and customer-re-runnable.

5 — Memory & learning tier

Vector plus structured store of past investigations (symptom fingerprint → confirmed root cause), imported runbooks, engineer corrections, and service metadata (owners, SLOs, escalation). Retrieved at the contextualize step; nightly consolidation prunes stale entries.

6 — Guarded remediation tier

  • Default read-only. An action requires: the action type on the tenant allowlist (rollback, scale, restart, feature-flag toggle), explicit human approval in chat, and a per-incident action budget (max N actions, then mandatory human takeover).
  • Every action: pre-state snapshot, execution through existing operators (ArgoCD rollback, scoped ServiceAccount), post-verification that the anomaly cleared, auto-report. Immutable audit log; scope violations self-reported as incidents.

7 — Interface tier

Chat-first Slack/Teams bot and web UI (natural language → investigation, trace query, topology question, or status, with rendered mini-waterfalls and evidence links). Grafana datasource plugin, REST/gRPC API, and an MCP server so other agents can query TraceIQ — while TraceIQ can consume Tempo's MCP server as a backend. Pages route to PagerDuty/OpsGenie with the RCA draft attached, not before it.

8 — Deployment model

Single-binary dev mode (embedded ClickHouse, local disk) growing into a Helm chart for production (collector DaemonSet, sampler StatefulSet, Kafka, ClickHouse cluster, brain deployment, external object storage). Multi-tenant with per-tenant retention, sampling, and allowlist policy. Works out of the box on Istio service-mesh telemetry.

08 · Conclusion

The empty intersection

The 2026 tracing landscape splits cleanly: open-source tools that collect traces economically but leave alerting, correlation, and root-cause analysis to humans — and commercial platforms that automate the analysis but charge unpredictably, cap retention, obscure their AI's reasoning, and lock the intelligence in. The new wave of AI SRE agents proves demand for automated investigation but sits atop those same proprietary platforms and stops short of trusted remediation.

TraceIQ occupies the empty intersection: an OpenTelemetry-native tracing bot that owns the full loop — anomaly-aware collection, cheap open storage, transparent evidence-grounded agentic RCA, natural-language access, and guarded remediation — on infrastructure you control at infrastructure prices. Its defining innovation is closing the loop between the agent and the sampler, guaranteeing the traces that matter are the traces that exist when the investigation starts.

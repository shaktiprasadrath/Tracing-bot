## W18-D1 — Span-level `service` attribution collapses to the trace's root service

**Severity:** High (data-quality / correctness; breaks per-span service
identity for every multi-hop trace, which topology, per-service search, and
several RCA rules depend on)

**Component:** `internal/store/store.go`, `TieredStore.Append`

**Status:** Fixed

### Fix

`internal/store/store.go:664` (in `TieredStore.Append`'s span-conversion
loop) now derives `SpanIndex.Service` from a new package-local `spanService`
helper (`internal/store/store.go`, added just above `Append`) that reads
`sp.Resource.ServiceName` for each span, instead of `t.RootService`.
`model.Span.Service()` is still a `panic("not implemented")` stub in
`internal/model/telemetry.go` and `internal/store` may not edit
`internal/model` (scope lock), so this mirrors the same local-helper pattern
`internal/sampler/spanutil.go`'s `spanService` already used for the same
constraint. `TraceIndex.RootService` (the trace-level summary field) is
untouched — only the per-span `Service` column was wrong.

Regression test: `TestAppend_SpanServicePerSpan_NotRootService` in
`internal/store/store_test.go` — builds a synthetic 3-hop trace (root/child/
grandchild spans from three different services sharing one `trace_id`),
appends it through `TieredStore.Append` against a real `sqlite.Store` hot
index, and asserts each returned span row's `Service` matches its own
originating service (and that `SearchSpans` filtered by a non-root service
now finds that service's spans). Confirmed failing against the pre-fix code,
passing after the fix; full `internal/store/...` suite and `go build ./... &&
go vet ./... && go test ./... -count=1` are green with no other test
assertions needing adjustment.

### Repro steps

1. Deploy TraceIQ (any config) and point real OTLP/gRPC traffic at it from an
   Istio mesh with more than one hop per logical transaction (e.g. the
   istio-tx-lab `bank` namespace: `mesh-client -> transaction-orchestrator ->
   payment-service` / `-> ledger-service`).
2. Send a handful of transactions so each hop's own sidecar independently
   exports its own OTLP spans for the same `trace_id` (real distributed
   tracing: N `ExportTraceServiceRequest` batches per logical transaction,
   one per hop, each carrying its own `Resource.service.name`).
3. Let the sampler finalize and flush a kept trace, then query the hot
   index: `SELECT service, operation FROM span WHERE trace_id = ?`.

### Expected

Each span row's `service` column reflects the OTLP resource that actually
produced that span (e.g. a payment-service-originated span should read
`service = "payment-service.bank"`, an orchestrator-originated span
`service = "transaction-orchestrator.bank"`, etc.) — this is what
`internal/ingest/otlp_normalize.go`'s `convertOTLPSpan` already attaches
per-span via `sp.Resource` before the sampler assembles the trace.

### Actual

Every span in a stored trace is written with `service = t.RootService` (the
trace's overall root/first-seen service), regardless of which resource the
individual span actually came from. Confirmed live: 92 real kept traces from
the W18 S13 (connection-pool-exhaustion) test, root_service = "mesh-client.bank"
(correct, mesh-client is the true distributed-trace root); every one of the
276 stored span rows across those traces was also stamped
`service = "mesh-client.bank"`, even spans whose `operation` field shows they
represent calls to `payment-service.bank.svc.cluster.local:8080` and
`ledger-service.bank.svc.cluster.local:8080` — i.e. spans that were, per the
OTLP normalizer's own per-span `Resource`, generated by
transaction-orchestrator's sidecar, not mesh-client's.

Root cause, `internal/store/store.go` around line 664 (`TieredStore.Append`):

```go
spans = append(spans, SpanIndex{
    Tenant:        tid,
    TraceID:       t.TraceID,
    SpanID:        sp.SpanID,
    Service:       t.RootService,   // BUG: should be sp's own resource service name
    Operation:     sp.Name,
    StartUnixNano: int64(sp.StartUnixNano),
    DurationNanos: sp.EndUnixNano - sp.StartUnixNano,
})
```

Every span in the trace is stamped with the trace-level `RootService`
instead of its own originating service. This did not surface in
`cmd/traceiq/system_smoke_test.go`'s smoke test because that test sends a
single-span, single-hop synthetic trace where root service and span service
are trivially identical — it only shows up with a real multi-hop trace,
which the live mesh test exercises for the first time.

### Impact

- `store.SearchSpans` filtered by `Service` cannot find spans from a
  non-root service — they are invisible under their real service name.
- Downstream consumers that group/filter spans by service (topology
  edge construction reading spans, `rca` rules that build
  `SpanTimingRow.ChildService`/similar from span-level service identity)
  will misattribute or fail to find evidence for any service but the trace's
  root.
- Not a blocker for this test's headline result (RCA still concluded
  correctly — see the report — because the verification harness supplied
  `EpicenterService`/evidence independently rather than relying on the
  broken `span.service` column), but it is a real, reproducible defect that
  should be fixed before `internal/store` is used for anything that needs
  per-span service identity (topology, per-service search, several RCA
  tools).

### Suggested fix

In `TieredStore.Append`, derive each `SpanIndex.Service` from `sp.Resource`
(or whatever per-span service field `model.Span` carries after normalization)
instead of `t.RootService`.

## Known, already-documented gaps confirmed still present (not new defects)

For completeness — these are pre-existing, already-documented limitations
(see `cmd/traceiq/stubs.go`, `cmd/traceiq/system.go`'s TODO comment) that
this test's step 9 verification program had to work around, not new findings:

- `internal/api` is not wired into `cmd/traceiq`'s `System` at all (no
  HTTP/MCP query surface). Verification had to go around the live pod
  entirely (copy the sqlite file out via `kubectl exec ... cat
  /proc/1/root/data/hot/traceiq.db`, since the distroless image also has no
  shell/tar for `kubectl cp`).
- `rca.NewRegistry`'s five tool backends (`TraceStore`/`LogStore`/
  `MetricStore`/`TopologyStore`/`MemoryStore`) are all wired to no-op stubs
  in `cmd/traceiq`. In particular this means the real, deployed TraceIQ pod
  can never confirm `connection-pool-exhaustion` (or any other
  `MetricQuery`-based rule) today, no matter how good the underlying
  incident evidence is — `noopMetricStore.MetricQuery` always returns an
  empty result. The rule's own logic was verified correct in this test by
  substituting a real evidence-backed `MetricStore` (fed from actual Envoy
  `503 UO upstream_reset_before_response_started{overflow}` access-log
  counts captured live during the S13 drill) in the standalone verification
  program — the *rule* fires correctly given real evidence; it is the
  *wiring* in `cmd/traceiq` that is the known gap.

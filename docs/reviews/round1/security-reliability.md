# Round 1 Architecture Review — Security & Reliability

**Reviewer lens:** Security and Reliability (Architecture Review Board)
**Date:** 2026-09-14
**Scope reviewed:** `Tracing-Bot-PRD.md`; `docs/architecture/00-feature-catalog.md`, `01-system-architecture.md`, `02-class-diagram.md`, `03-sequence-diagrams.md`, `04-execution-flow.md`, `05-tool-selection-adr.md`; `docs/architecture/features/F01–F12`, `X-SEC`, `X-OPS`; `docs/ledger.md`.

## 1. Verdict

> ## **APPROVE-WITH-CHANGES** — blocking on SR-1 … SR-7.

The architecture is fundamentally sound and, in places (`04-execution-flow.md` §4–§6, `03-sequence-diagrams.md` §5–§6, `01` §8.6/§8.7), it is materially better than most production systems at this stage. The blockers are not architectural dead-ends; they are **specification defects** — mostly places where the strong control described in an overview document (`01`, `03`, `04`) is *absent, weaker, or contradicted* in the feature document an engineer will actually implement from (`F01`, `F02`, `F03`, `F06`, `F09`, `F10`, `F12`, `X-OPS`).

That distinction matters, because the feature docs are the build contract. Where `01` §8.6 says the Guard re-resolves targets against the topology graph and `F09` §4.4 does not, the code will be written from `F09`. Every blocker below is of that form or worse.

**Gating:**

| Work | Status |
|---|---|
| F01–F05, F07, F08 implementation | May proceed once **SR-3, SR-6, SR-7, SR-8** text lands (they change ingest/store contracts). |
| **F06, F09, F10, F11, F12 implementation** | **Blocked** until SR-1, SR-2, SR-4, SR-5, SR-6 close and a round-2 re-review signs off. |
| Any listener bound beyond loopback, on any branch | **Blocked** until SR-3 and SR-23 (toolchain) close. |
| Publishing an external artefact / demo | Blocked until SR-23 closes (`govulncheck` clean). |

There is one finding I want to name in the verdict rather than bury in a table, because it is the review's central result: **SR-1 establishes a live path from attacker-controlled telemetry content to a cluster mutation payload.** Every other prompt-injection defense in the design is good; this one path defeats them, because it does not require the model to escape its schema — it only requires the model to fill a legitimately-schema'd free-form field (`Action.Params["patch"]`) that nothing downstream semantically validates.

## 3. Answers to the standing review questions

Brief, because the table carries the detail — but these were asked directly and deserve direct answers.

**Is there any path where telemetry content can influence an action?** **Yes — three.** (1) `Action.Params["patch"]` → `kubectl patch` with syntax-only validation (SR-1); this is the serious one. (2) The approver's decision input — `Rationale`, the report narrative, and the Slack message body are all model-authored from telemetry-influenced evidence, and no doc requires the approval UI to mark them as untrusted or to show the *computed payload* rather than the prose. (3) `sampler.InterestPredicate`, derived from the report (`derivePredicate`, `03` diag 6), which controls retention and therefore cost — bounded by `max_keep_rate` in `01`/`03`, unbounded in `F02` (SR-10). Add: memory makes (1) and (2) **persistent** across incidents (SR-13).

**Are the F06/F10 prompt-injection defenses sufficient and testable?** The *structural* defenses are genuinely good — no raw span dumps, delimited untrusted regions with escaping, strict schema output, a closed five-tool registry, no URL/host arguments, a canary echo check, and hard budgets (`01` §8.6). Two problems: they are described three different ways across `01` §8.6 (delimiters), `X-SEC` §4.4 (message roles), and `F06` §4.4 (typed JSON), so an implementer gets to choose; and the containment they provide is undone downstream by SR-1 (the schema-legal free-form patch field), SR-12 (the schema-legal free-form query field), and SR-13 (persistence). They are testable — AC-XSEC-7 and AC-F06-3 are well-formed — but both corpora test only "did an unauthorized *tool call* or *execution* occur". Neither tests "did injected content change the **content** of a proposed action or a query", which is the actual failure mode. Add that assertion.

**Can the F09 state machine be bypassed?** Yes, four ways as specified: approval replay after TTL (SR-4), auto-execute collapsing the second gate (SR-4), budget exhaustion evaded via `failed`/rolled-back actions (SR-5), and approval identity being unbound to any principal (SR-2). kubectl **argv** injection is genuinely well-handled (`[]string` argv, per-type regex, `no-shell-interpolation` CI gate, a 50-case fuzz AC) — the hole is the **payload**, not the argv. Rollback safety is unsound against concurrent modification (SR-27). Note one internal inconsistency worth fixing while you are in there: `ActionTarget.Resource` is documented as `"deployment/checkout"` while `validate()`'s regex `^[a-z0-9]([-a-z0-9]{0,61}[a-z0-9])?$` rejects `/` — and the argv builder then prepends `"deployment/"` to it.

**Do F09 / F12 / X-SEC agree on the RBAC matrix?** No. Execute is operator (`01` §8.2), approver-or-admin (`F09` §4.3), and ≥approver (`X-SEC` FR-XSEC-3). Audit read is admin (`01` §6.1) and viewer-redacted (`F09`/`F12`). MCP is per-tool (`01` §6.2) and endpoint-level operator (`F12`). Chat is role-free (`F10`/`F12`) and principal-resolved (`03` diag 4). `X-SEC`'s hierarchy `admin ⊇ approver ⊇ operator` also silently grants every approver the operator capabilities, which interacts with separation of duty in a way no doc discusses (an approver can propose, then a second approver approves — fine; but the hierarchy is never stated as intentional).

## 4. Positive notes — do not regress these while fixing the above

These are genuinely strong, and several fixes above could damage them if applied carelessly. Protect them explicitly in round 2.

1. **`04-execution-flow.md` §4–§6 is the best artefact in the set.** Every channel has a capacity and a named full-behaviour; backpressure is traced end-to-end from slow disk to a 429 at the receiver; the six steady-state invariants ("bounded everything", "nothing is lost silently", "fail-closed on audit", "the LLM is never load-bearing") are the right invariants, stated crisply. **The fix for SR-8 must be to make `F01` match `04`, never the reverse.**
2. **Fail-closed on audit** (`04` §5.2, `X-SEC` §5): "an action that cannot be audited does not happen." Rare, correct, and easy to lose when someone hits an availability problem. Keep it.
3. **RED extraction strictly before any discard** (`01` §3.1/§8-flow, `F02` FR-F02-5, `03` diag 1), with `sampler.red.extract_before_discard: true` rejected at validation if set false. This is what makes aggregate accuracy survive sampling; it is the technical core of the PRD's wedge.
4. **Degradation is designed, not hoped for** (P7, `04` §3/§5.2): LLM → rules mid-loop; cold store → WAL spill with ingest continuing; correlation adapters → explicit `ErrAdapterUnavailable` recorded as a **named missing-evidence class in the report** rather than a silent gap. The last detail is excellent and unusual.
5. **The transparency/replay contract** (`01` §4.4, `03` diag 7): `ToolArgsJSON` + `ToolResultHash` + `ReplaySeed`, replay defaulting to cached results at zero cost, live replay diffing hashes to distinguish *reasoning error* from *data drift*, corrections appending as a new investigation with `ParentID` while the original stays immutable. This is a materially better answer to D-Y1 than the competitors it is aimed at.
6. **`01` §8.7 SSRF defenses**: single egress dialer, DNS pinned per connection against rebinding, redirects not followed, `169.254.169.254` refused **unconditionally in every mode**. Keep the unconditional wording — SR-21 asks for more, not less.
7. **`03` diagram 5's guard sequence** is stronger than `F09` and should be the template for the SR-1/SR-4 rewrite: `resolveTarget` against the live topology graph, `TargetMatcher` globs, budget check, snapshot, dry-run diff shown to the approver, `SeparationOfDuty`, explicit `Expired` branch, `scope_violation` self-reporting on a Kubernetes RBAC denial. Most blockers in this review are "make `F09` say what diagram 5 already says."
8. **ADR §7.1 is a model of honest architecture writing.** It found a 25-vuln reachable set on its own chosen toolchain, published the counts, named the one that cannot be fixed within the pinned line (`GO-2026-6061`), explicitly refused to wave it away as "we don't use xDS", separated the 4 free fixes from the 21 that are not, and declared FU-1 a blocker against its own decision. SR-23 sharpens the sequencing; it does not dispute the analysis. The `GOTOOLCHAIN=local` discipline and the "deliberately absent" dependency list are exactly right — the ask is to mechanize them, not to relax them.
9. **Dependency minimalism as a security control** (`ADR` D-6/D-9/D-10/D-11): stdlib `net/http`, no vendor LLM SDK (~100 modules and two cloud auth stacks avoided for one JSON POST), no React/Vite in the release build, no testify, CGO forbidden. 73 modules total for a system of this scope is a real achievement and directly serves the product owner's "natively" requirement.
10. **An anomaly is an incident, not a page** (`01` §9 D-D4, `03` diag 2, `02` §4): topology-proximity grouping, dedupe TTL, investigation-gated alerting with the RCA attached. Keep the design; SR-14 only asks for a deadman path so that the gate cannot become a silent drop.
11. **`eval.HarnessRunner` drives the real pipeline through the real receivers** with no bypass (`02` §4 note), and eval fixtures are tagged `synthetic=true` and excluded from production memory retrieval (`F11` §6). That exclusion is precisely the kind of thing usually discovered in production; it was designed in.
12. **Honest open-question sections throughout.** `F09` §8 flags its own budget-counting ambiguity and the auto-rollback exemption; `X-SEC` §8 flags its own incomplete STRIDE table and missing revocation design; `X-OPS` §8 admits the capacity table is unvalidated. Several findings above are upgrades of the authors' own flags — that is a healthy document set, and the habit should survive round 2.

## Findings

| # | Severity | Area | Finding | Status |
|---|---|---|---|---|
| 1 | **Major (bug)** | `internal/topology/livegraph.go` `upsertEdge` | `lastNewEmit[key]` was only refreshed when `isNew` was true. §4.4's pseudocode calls for `recentEdgeSet.addWithTTL(key, newEdgeWindow)` **unconditionally on every upsert** (a refreshing TTL). Under continuous traffic, `lastNewEmit` stayed pinned at the edge's original first-sighting time forever, so ~24h after that first sighting the edge would spuriously re-fire `ChangeEvent{NewEdge}` even though it never actually went quiet — a false "new edge" signal that reaches F05's anomaly detector. Violates FR-F04-6 / AC-F04-6 ("no re-emission within the window"). No existing test covered a multi-day continuous-traffic scenario, so this shipped silently. | **FIXED** — `lastNewEmit[key] = ts` now runs unconditionally on every `upsertEdge` call, matching §4.4's `addWithTTL` semantics. Regression test `TestUpsertEdge_ContinuousTrafficDoesNotReemitNewEdgeAcrossWindow` added (30 hourly consumes past the 24h window, asserts zero re-emission); verified it fails against the pre-fix code by tracing the logic (hour 25 crosses `ts.Sub(t0) > 24h` under the old always-pinned anchor). |
| 2 | **Major (gap)** | `internal/topology/livegraph.go` | No production driver existed for the periodic work F04 §4.1/§4.4 requires: 10s `Flush`, 1m `VanishSweep`, and the pending-correlation-buffer sweep. `sweepVanished`/`sweepPending`/`Flush` were only ever invoked directly by tests. The package's own comment on `sweepVanished` said "production use is a background ticker (see Run)" — but no `Run` method existed anywhere in the package. Net effect: `VanishedEdge` detection (FR-F04-6) and `EdgeSink`-backed durability/warm-start would never fire outside a test process. | **FIXED** — added `LiveGraph.Run(ctx)`, a `model.Clock`-driven loop (DR-31 compliant, confirmed by `archtest`) that ticks Flush (10s), VanishSweep (1m) and pending-buffer sweep (`pendingTTL/2`) until `ctx` is cancelled. `config.TopologyConfig` has no `flush_interval`/`sweep_interval` fields (same gap already present on `newEdgeWindow`/`pendingTTL`), so the intervals are package constants matching F04 §4.3's documented defaults — promoting them to config is a follow-up, documented inline. Regression test `TestRun_DrivesFlushAndVanishSweep` added (fires the flush and vanish tickers via a new controllable `fakeTicker`, asserts `EdgeSink.WriteEdges` and a `VanishedEdge` on `Changes()` both actually happen, and that `Run` returns `context.Canceled` on shutdown). **Still not wired into `cmd/traceiq`** — nothing in `cmd/traceiq/main.go` references `internal/ingest` or `internal/topology` at all yet; calling `Run` per tenant-scoped `LiveGraph` instance at boot is `cmd/traceiq`'s job, out of this package-level review's scope, same as ingest's already-documented deferred wiring. |
| 3 | **Major (gap)** | `internal/ingest/limits.go` `applyLimits` | §4.4's `HandleInbound` pseudocode checks `sizeOf(batch) > ingest.limits.max_batch_bytes` before tenant resolution. `config.IngestLimitsConfig.MaxRequestBytes` (4 MiB, DR-26 §26.4) existed and `model.Batch.SizeBytes` was already populated by every `Normalizer` (`proto.Size`/`len(body)`) — but nothing ever compared the two. Only span **count** (`MaxSpansPerBatch`) was enforced, not byte size. A batch at or under the count cap could still carry an arbitrarily large payload (e.g. via deeply nested `AnyValue` attributes, which `attrValueApproxBytes` also under-counts — see Finding 5) and sail through, undermining §6's "closing a class of malformed-input DoS/parser-exploit vectors" claim and FR-F01-8/AC-F01-6. | **FIXED** — `applyLimits` now rejects (`ReasonOversize`, matching `INVALID_ARGUMENT`/400) any batch whose `SizeBytes` exceeds `MaxRequestBytes`, mirroring §4.4 exactly. Regression test `TestApplyLimits_OversizeRequestBytesRejected` added. |
| 4 | **Major (gap, not fixed — cross-package)** | `internal/topology` + `internal/store` | DR-13's "`Changes()` is lossless for `NewEdge`" guarantee (FR-F04-6, AC-F04-9) requires every new edge to be durably recorded as `topology_edge_meta.is_new = 1, first_seen` so `anomaly.TopologyChangeDetector` can reconcile from that table every 30s tick, bounding channel drop-oldest loss to one tick. **No such table or write path exists anywhere in the repo** — `topology.EdgeSink` only has `WriteEdges([]Edge)`, `store/sqlite`'s `WriteEdges`/`LoadEdges` never touch `is_new`/`first_seen`, and `Edge.IsNew`/`IsVanished` are computed in-memory but never persisted by `store/sqlite`'s `WriteBatch`. Today, a `NewEdge` dropped by the 256-cap drop-oldest channel (e.g. during an F05 outage) is lost permanently — the AC-F04-9 guarantee does not hold. | **Not fixed in this pass.** Closing it correctly needs a store schema addition (`topology_edge_meta` table) and a new/extended `EdgeSink`-family interface, which touches `internal/store/sqlite` and the not-yet-built `internal/anomaly` reconciler — outside this review's `internal/ingest`/`internal/topology` file scope and risky to improvise without the store-schema owner. Flagged for a dedicated follow-up pass. |
| 5 | Minor | `internal/ingest/limits.go` `attrValueApproxBytes` | Returns a constant `8` for `AttrSlice`/`AttrMapK`, ignoring actual nested content size, so the per-attribute `MaxAttributeValueBytes` cap never fires on a large nested array/map attribute. In isolation this was a real gap; after Finding 3's fix, the whole-batch `MaxRequestBytes` check (measured via `proto.Size`, which does account for nested structure) now acts as a backstop, so the residual risk is a large-but-under-request-cap nested attribute skipping per-attribute truncation/flagging. Not fixed here (would need a recursive size walk plus deciding how "truncate" should behave for a nested type, which `truncateAttrValue` doesn't currently support) — flagged as a follow-up. |
| 6 | Minor (architecture note, no bug found) | `internal/ingest` fan-out (`Server.Ingest` → `sinkQueue.push`) | The same `batch.Spans` slice (and its nested `Attrs`/`Resource`/`Events`/`Links` reference types) is handed to every registered sink's queue and consumed by independent, concurrently-running drain goroutines — matches §4.4's pseudocode (`outputQueue[sink].push(batch)` for every sink), so this is intentional, not a deviation. Checked both current consumers: `topology.LiveGraph.Consume` only reads span fields; `sampler.Manager.Consume` writes `s.Tenant` (already stamped by ingest before fan-out, so effectively a no-op) and otherwise copies `*s` by value before storing it. No two sinks currently touch the same struct field concurrently, so there is no live data race today — but nothing enforces "consumers must treat the shared batch as read-only," so a future sink implementation mutating a field topology also reads (e.g. `Attrs`) would introduce a real race with no compiler/test signal. Worth a doc comment on `SpanSink.Consume` making the read-only contract explicit; not fixed here as it's a documentation-only, non-blocking suggestion. |
| 7 | Confirmed, not a gap | `internal/ingest` — OTLP-HTTP/Jaeger receivers, auth/TLS, real Prometheus metrics | Matches the task's framing: `otlpgrpc` is real and wired; `otlphttp`/`jaeger` normalizers/receivers, TLS, and full principal extraction are absent and clearly documented in-code (`otlpgrpc.go`, `metrics.go`) and in `docs/reports/w9-ingest-cont.md` as deferred pending X-SEC's auth package and time-boxing, not silently dropped. `subjectFromContext` fails closed (empty subject → `tenant.Resolver` rejects `UNAUTHENTICATED`) for every mode except the explicit dev-default path. This is legitimate scope reduction, not a disguised gap — nothing here blocks approval. |
| 8 | Test quality | Both packages | All tests found are real, specific assertions (exact field values, exact error `Reason`/gRPC code, exact edge/attribute contents) — no "just checks no panic" tests in either `ingest_test.go` or `livegraph_test.go`. Coverage gaps that *do* exist: no test for `MaxRequestBytes` before this pass (now added), no test for continuous-traffic `NewEdge` non-re-emission before this pass (now added), no test at all for `Run`/background driving before this pass (now added), and no test exercising `internal/store/sqlite`'s `WriteEdges`/`LoadEdges` round-trip of `IsNew`/`IsVanished` (relevant to Finding 4, out of this review's package scope). | — |

# w16 — Security-critical review: `internal/rca` LLM reasoner

**Scope:** `internal/rca/llm_reasoner.go`, `sanitizer.go`, `schema.go` and their
tests (`llm_reasoner_test.go`, `llm_reasoner_loop_test.go`,
`engine_llm_test.go`, `engine_llm_budget_test.go`), reviewed against
DR-17 (budget), DR-34 (Anthropic client contract, mid-loop fallback), DR-18
(replay), DR-37 (prompt-injection defenses / STRIDE) and DR-16 (closed tool
set / SSRF). No `docs/reports/w15-rca-llm.md` spec exists in this checkout;
the register sections above were read as the binding source instead.

No goroutines, unclosed timers, or other resource-leak patterns were found in
`llm_reasoner.go`; `engine.go`'s per-step `context.WithTimeout` is `cancel()`d
on every exit path of the loop, including both branches of the mid-loop
fallback swap.

## Verdict: **APPROVE-WITH-FIXES** (fixes applied in this pass)

Two Major issues were found and fixed in this session (see table). Everything
else is Minor/informational — none block merge.

## Findings

| Sev | File:Line | Issue | Fix |
|---|---|---|---|
| **Major** | `llm_reasoner.go` (`buildPrompt`, "Hypotheses on the board" block, pre-fix ~line 221-226) | `Hypothesis.ID/Statement/Component` are **model-authored** (from a prior turn's LLM output) but were rendered into every subsequent turn's prompt **unwrapped and unescaped** — no `Sanitizer.Wrap`, no `<`/`>` escaping. Since the model can (under injection, or by innocently quoting suspicious telemetry while describing a hypothesis) copy attacker-controlled telemetry text into `Statement`, this was a genuine unwrapped-telemetry-reaches-the-prompt path per DR-37 §37.1(2) ("every string not authored by TraceIQ's own code"), and the missing escaping meant a hypothesis could forge literal `<untrusted ...>` delimiter bytes. Not caught by the existing test suite — both `buildPrompt` tests construct `State`s with empty `Hypotheses`. | **FIXED.** The whole hypothesis-board block is now rendered into one string and passed through `san.Wrap(model.UntrustedTelemetry, ...)`, exactly like the tool-result digest. New test `TestBuildPrompt_WrapsHypothesisBoardState` proves the wrap and the escaping (an injected `<fake>` marker does not survive raw). |
| **Major** | `schema.go` (`ValidateReasonerOutput`) | `Hypothesis.PostScore` had **no range check**. `LLMReasoner.Conclude` uses `PostScore` directly as `Investigation.Confidence`, compared against `confidenceThreshold` (0.75) to decide `Concluded` vs `Inconclusive`. An out-of-range value (e.g. `post_score: 999`, or negative) — whether hallucinated or injection-induced — could force a spuriously "confident" conclusion or corrupt the best-hypothesis comparison. Separately, `Statement`/`Component`/`ID` had **no length cap** (only `Rationale` was capped, at 2000 bytes) — an unbounded hypothesis string re-enters every later prompt (per the finding above) and is a real token/cost amplifier against DR-17 §17.1's worked per-step budget arithmetic. | **FIXED.** Added `post_score ∈ [0,1]` validation and length caps (`maxHypothesisIDBytes=128`, `maxHypothesisStatementBytes=500`, `maxHypothesisComponentBytes=200`) in `ValidateReasonerOutput`. New tests: `TestValidateReasonerOutput_RejectsPostScoreAboveOne`, `RejectsNegativePostScore`, `RejectsOversizedStatement`. |
| Minor | `llm_reasoner.go` (`buildPrompt`, `epicenter service %s` line) | `Incident.EpicenterService` is telemetry-derived (an OTel `service.name` resource attribute is client-supplied in most real deployments) and renders unwrapped. Left unchanged: it is Incident-level metadata assigned upstream by F05 anomaly detection/topology, not authored by this wave's code, and an existing test (`TestBuildPrompt_NoLastResultMeansNoUntrustedBlock`) explicitly asserts *no* untrusted block appears with no `LastResult` — wrapping this field would need to touch that contract and verify upstream service-name validation (topology/ingest) first. | Not fixed — flagged for a follow-up that first confirms whether ingest-time validation already constrains `EpicenterService` to topology-known names. |
| Minor | `errors.go` / `llm_reasoner.go` (`isFallbackTrigger`) | DR-34 §34.4's table specifies **thresholds** before a swap (3 consecutive transport failures, 2 refusals, 2 canary violations), but this implementation swaps on the **first** occurrence of each. This is documented deliberately in code comments as the conservative choice (fails toward the safer, earlier fallback rather than under-triggering) and does not create a security hole — it is stricter, not laxer, than spec — but it is a real spec-conformance gap against DR-34 §34.4 verbatim. | Not fixed — pre-existing, intentional, documented tradeoff; flagged for the register/spec to either bless the simplification or for a later wave to add the Engine-level consecutive-failure counters DR-34 actually describes. |
| Minor | `schema.go` (`ValidateToolArgs`) | DR-16 §16.3's topology-existence check ("`Service` ... must be present in `topology.Graph.Snapshot`") is only applied when `LLMReasoner.Topo` is non-nil; no production call site wires `Topo` yet (`grep` found none in `cmd/` or `internal/eval/`), so today this defense is dormant everywhere it would run for real. The `urlOrHostPattern` regex also only catches `scheme://` and bare-IP:port shapes, not a bare attacker-chosen DNS hostname with no scheme (e.g. `internal-metadata.svc.cluster.local`) — the topology check is what was meant to close that gap, per §16.3. No functional impact **yet**: all 5 `Tool.Invoke` implementations dispatch to a consumer-declared backend interface (`TraceStore`/`LogStore`/...) that is either `nil` (→ `ErrToolUnavailable`, no network call) or, in tests, an in-memory fake — real backends are explicitly a later wave (`tools.go`'s doc comment). | Not fixed — no current code path reaches a real network call, so nothing to fix now; flagged so `Topo` is wired at the same time real backends land, not after. |
| Minor | `tools.go` (`fiveToolSchemas`) | `InputSchema` sent to the model is a placeholder (`{"type":"object"}`) for all 5 tools rather than the real per-tool JSON Schema; the model is only told the shape via the system-prompt English description. Already self-documented as a wave deferral. Functional/quality risk (the model may guess wrong field names), not a security hole — `ValidateReasonerOutput`'s strict decode rejects whatever it gets wrong anyway. | Not fixed — documented deferral, acceptable. |
| Minor (test coverage) | `engine.go` loop-top checks | `TermToolCalls` and `TermCost` are enforced by the same simple comparison pattern as `TermSteps`/`TermWallClock` (both of which are tested), but neither has a dedicated engine-loop test exercising the Engine actually terminating the loop for those two specific reasons (only the `LLMReasoner`-level *preflight* budget check for tool-calls is tested, in `TestBudgetPreflightExceeded`/`TestLLMReasoner_NextStep_BudgetExceededSkipsTheCallEntirely` — that is a different code path from the Engine's own loop-top check). | Not fixed — recommend a follow-up test analogous to `TestInvestigate_LLMTokensBudgetExhausted` for `TermToolCalls`/`TermCost`. |

## Security-property pass/fail

- **Telemetry-wrapping:** FAIL as found → **PASS after fix.** `LastResult` digests were always correctly wrapped (verified in code and by `TestBuildPrompt_WrapsTelemetryTagAndCanary` / `TestLLMReasoner_NextStep_RequestNeverCarriesRawUnwrappedToolResult`, both genuine assertions on the constructed request, not just internal state). The one real gap — model-authored `Hypothesis` fields round-tripping unwrapped into later-turn prompts — is fixed and now covered by `TestBuildPrompt_WrapsHypothesisBoardState`.
- **Schema-validation:** PASS, with gaps fixed. `ValidateReasonerOutput` genuinely rejects (not logs-and-continues) unknown fields (`DisallowUnknownFields`), trailing JSON, unknown enum values, and multi-payload tool calls, verified by real tests and by constructing adversarial payloads myself (unknown category/phase, trailing data, `post_score:999`, oversized statement) — all correctly rejected pre- and post-fix except the two now-fixed range/length gaps. A rejected proposal never carries a `Call` (`TestLLMReasoner_NextStep_RejectsSSRFShapedToolArgBeforeDispatch` explicitly checks `prop.Call == nil`).
- **SSRF-defense:** PASS for this wave's actual code paths. All 5 `Tool.Invoke` implementations either return `ErrToolUnavailable` (nil backend, the state of every production call site today) or delegate to a test fake — no real network call exists anywhere in this wave's reachable code. The regex + optional-topology defense-in-depth layer has a real gap (bare-hostname strings, and `Topo` unwired in production) but nothing currently exercises it against a live network, so it is a forward-looking Minor, not a live hole.
- **Prompt-injection-resistance:** PASS after fix, with residual risk stated. Direct telemetry→prompt is correctly wrapped, escaped, and canary-monitored (`CheckEcho` checked before the output is trusted enough to parse). The second-order path — injected content laundered through a model-authored `Hypothesis.Statement` back into a later, unwrapped prompt — was real and is now closed. Irreducible residual risk (inherent to LLM-based reasoning, not a code defect): a successful injection can still steer the model to a schema-valid, SSRF-clean tool call or an incorrect-but-well-formed conclusion; this wave's defenses (delimiters, canary, strict schema, closed tool set, now-fixed score bounds) reduce but cannot structurally eliminate that, matching DR-37's own "defense in depth" framing.
- **Fallback-correctness:** PASS. The fallback path is genuinely reachable and tested with real triggers, not a mock that always succeeds: `TestFullLoop_LLMReasoner_TransportFailureFallsBackToRealRulesReasoner` and `TestFullLoop_LLMReasoner_SchemaInvalidFallsBackAndConcludesGracefully` drive the full `engine.Investigate` loop with `llm.MockClient` returning real errors/malformed JSON and a **real** `rules.New()` as the swap target (not a stub), asserting the swap is recorded, prior steps survive, confidence is capped, and the investigation reaches a graceful terminal status. `TestInvestigate_FallbackTriggerWithNoFallbackWiredFailsGracefully` proves the no-fallback-wired case fails gracefully (`TermFailed`, no panic) rather than hanging or silently succeeding.
